## N2 — decision event conflates attempted acceptance with granted approval

**Source:** `apps/toolgw/src/tool-approval.ts:388-408`; regression `apps/toolgw/src/tool-approval-check.ts:1184-1196`; R9 rationale `docs/spikes/stellarc-approval-expiry-r9.md:61-64,149-152`.

Both a successful approval and an acceptance whose audit wait crosses expiry append `kind='tool.approval.accept'`, with the identical payload `{approval: id, human}`. On the latter path the guarded UPDATE misses, an expiry event is appended, the transaction commits, and the caller receives `410 expired`. The check explicitly expects one accept event and one expiry event for that refusal. The new comment and report call the first event an attempt, but neither an attempt-specific kind nor an outcome discriminator is present in the persisted contract.

The two-event sequence is insufficient to infer whether approval ever occurred: a real approval followed later by ordinary expiry can also produce accept then expired. Joining the current row cannot reconstruct that historical distinction either. The shared audit schema/store (`packages/core-auth/src/store.ts:26,54-75`) carries the supplied kind/payload unchanged; it adds no decision outcome. A downstream consumer treating `tool.approval.accept` as a successful human grant can therefore record a false grant or drive an incorrect projection. This is a concrete event ambiguity, **not a demonstrated external dispatch bypass**: the reviewed claim still requires the database state and its guarded transition. No downstream consumer was reviewed or asserted exploitable.

**Smallest change:** retain audit-first ordering but identify the first record explicitly as a decision attempt, and emit the existing success-kind event only after a winning decision UPDATE, in the same transaction. On miss, commit only the distinguishable attempt plus expiry. Equivalently, use a mandatory machine-readable attempt/outcome contract with an unambiguous success record; documentation alone is not enough. Audit failure at either append must still roll back the transaction. Adjust the existing decide-window oracle to assert the refusal has no success-accept event, and the ordinary successful-decision oracle to assert exactly one. No external write or product edit was made by this reviewer.

## Lock, transition, miss and rollback semantics

- **Lock acquisition and initial reads:** `store.transaction` awaits `sql.begin`, acquires `pg_advisory_xact_lock(719324821)`, then invokes the callback (`packages/core-auth/src/store.ts:76-90`). Claim and decide subsequently lock their selected approval with `FOR UPDATE` and compute `(expires_at>clock_timestamp()) AS live` (`tool-approval.ts:367-368,430-431`). Time spent waiting for the global lock precedes those DB-time reads. No application-clock authority remains; a mechanical source count found zero `Date.now` occurrences in the module.
- **Decide's awaited windows:** after the approval read, the human-principal query and action-audit append can cross expiry. The shared UPDATE for accept/decline/cancel checks `state='pending' AND expires_at>clock_timestamp()` after both (`:370-404`). A miss calls `markExpired` and returns `Committed` refusal; the exception is raised only after the transaction resolves (`:405-413`). The extra guard covers decline/cancel too, not just acceptance. A successful UPDATE records the decision at that transition, even if later transaction completion occurs after the deadline.
- **Claim's awaited windows:** lazy expiry is DB-derived, then digest/envelope validation is synchronous and the authority callback is awaited (`:433-473`). False recheck commits `claim_denied` and releases no payload (`:474-486`), even if the deadline crossed meanwhile; it need not also eagerly expire that row to remain safe. A thrown callback error rolls back. A true recheck reaches the guarded UPDATE (`:488-489`); a deadline-crossing miss persists expiry and returns refusal (`:490-498`). No claim event or returned payload exists on that miss.
- **Why miss means expiry here:** after checking the expected state, this transaction retains the row lock through its awaited work. With the supported store writers and a non-mutating authority callback, another transaction cannot replace the state between that check and UPDATE. Thus a miss is explained by the deadline predicate. The trusted `ClaimRecheck` receives a transaction capable of writes; arbitrary mutation of the approval by that callback, custom mutating triggers, and administrative interference are outside this primitive's contract, not new supported concurrency cases.
- **Expiry audit exactness:** `markExpired` audits first, then updates pending/approved (`:263-275`). Its callers hold the row lock and have established an eligible prior state. One winning refusal therefore persists one expiry event and transition; subsequent claim cannot re-enter that transition. Recovery uses conditional UPDATE-before-audit with a zero-row early return (`:566-606`), so a stale recovery candidate cannot add another expiry event after this refusal. No new timer/replay route was introduced.
- **Rollback:** `audited` propagates `Denied` or maps an ordinary audit error to `audit_denied` (`:246-262`). The audit sequence update and event INSERT use the same supplied transaction (`store.ts:65-74`). Failure rejects `sql.begin`, rolling back both audit work and approval changes; a committed-refusal sentinel cannot catch or turn that failure into a commit. For decide, failure of the expiry audit also rolls back the earlier attempted-action event. `audit_capacity` may separately persist the system gap marker (`store.ts:85-87`), not an approval transition.
- **After a winning claim:** its claim-audit append and commit are still awaited before returning payload (`:500-528`). They can finish after `expires_at`. This repair enforces deadline eligibility **at the winning UPDATE**, not a wall-clock guarantee at payload delivery, transaction commit, or network send. That is the bounded N1 repair requested by R8, not proof that every later boundary precedes expiry. Integration must preserve an explicit authorization linearization and the separate-send limits in R8; do not silently advertise a stricter deadline guarantee. `report` intentionally remains able to settle a previously claimed dispatch after approval expiry (`:531-563`).
