## N1 — HIGH: an approval can expire during recheck and still release its payload

**Exact source:** `apps/toolgw/src/tool-approval.ts:424-428,463-479` (`claim`); expiry semantics originate in `:58,349` and the refusal at `:425-428`.

`claim` checks `expires_at` against application time before opening the payload and awaiting `ClaimRecheck`. After the callback resolves `true`, its winning UPDATE checks only `id` and `state='approved'`; it does not check expiry again. A claim started just before expiry can therefore wait in a legitimate DB-only recheck until after expiry, then commit `dispatching` and release arguments. Recovery cannot intervene while that transaction holds the global advisory lock. A long or unbounded callback is not required: even a short DB wait can cross the remaining TTL. Application-clock skew can also disagree with the database that set the deadline.

This is **newly confirmed in R8, not claimed to have been introduced by R7's typing edits**. F1's rollback repair remains correct, but it does not close this separate expiry-at-consumption gap. A generic credential/rights recheck does not repair approval expiry automatically.

**Smallest fix:** use database time at the actual transition. After the awaited recheck, condition the winning UPDATE on `expires_at > clock_timestamp()`; on expiry, persist the expired transition plus exactly one expiry audit and return the existing `Committed` refusal so denial is raised only after commit. Keep audit failures inside the transaction. Align lazy expiry checks with DB time rather than relying on the application clock. Do not add a timer, second transaction, or replay mechanism.

**Smallest missing regression:** admit/approve a short-lived row; enter a held recheck before expiry, hold until the database observes expiry, then return `true`. Assert refusal, no returned payload, state `expired`, exactly one expiry event and zero claim events. An audit-insert-denial variant must leave the prior state intact and release nothing. This review did not run that regression; the current check has no held-recheck-crosses-expiry group. This is an expiry-contract defect, not a request for new fairness or scheduling work.

### R7 semantic checks, beyond compilation

- **Row shaping preserves the digest:** `apps/toolgw/src/tool-approval.ts:436-447` carries `id`, org, actor, subject, delegation, run, operation, binding and request digest into `contextDigest` (`:166-191`). `run_id` becomes `runId`; `request_digest` becomes `requestDigest`; database NOT NULL constraints are at `:50,53`. Null delegation still hashes as the empty string. No field that formerly bound ciphertext is dropped, including `id`. The same shaped record feeds the authority callback. This is not runtime schema validation of a raw SQL row, nor does it authenticate caller-supplied context.
- **Projection parse preserves JSON meaning, not textual jsonb bytes:** `:304-315,349` serializes once, bounds that serialization, parses it, then hands a JSON value to `tx.json`. Parsing removes executable getters / `toJSON` behavior from the subsequent serialization and preserves the serialized JSON value. PostgreSQL jsonb may normalize key ordering/representation; the comments and R7 report's “identical bytes” language must be read as JSON-value semantics, not a byte-equality guarantee. No new high blocker found in this change. This is still not a redactor, object-schema validator, or proof a human saw exactly the executor request.
- **Audit rollback is real at the existing boundary:** `audited` (`:246-262`) propagates `Denied` or converts ordinary audit failures to safe `audit_denied`. `store.audit` mutates sequence and inserts the event through the supplied transaction (`packages/core-auth/src/store.ts:54-75`). Recovery's update-before-audit order is safe because audit failure rejects that same transaction. A committed gap marker on `audit_capacity` (`store.ts:85-87`) is deliberately separate, not a committed approval transition.
- **No replay path added:** recovery only classifies; it never opens the envelope, calls `execute`, or returns a row to `approved`. At most one committed payload claim is supported. Exactly-once external execution is not established.
